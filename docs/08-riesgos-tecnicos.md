# 08 — Riesgos Técnicos

| # | Riesgo | Impacto | Probabilidad | Mitigación |
|---|---|---|---|---|
| R-01 | Condición de carrera entre ofertas casi simultáneas sobre el mismo lote produce un ganador incorrecto o ambiguo | Muy alto (rompe la promesa central del producto) | Media-alta bajo carga | Lock a nivel de fila en PostgreSQL al validar/aceptar cada oferta; Postgres como única fuente de verdad. Ver [ADR-004](adr/ADR-004-concurrencia-en-determinacion-de-ganador.md) |
| R-02 | Escalado horizontal de WebSockets: un cliente conectado a la instancia A no recibe eventos originados por una oferta procesada en la instancia B | Alto (rompe tiempo real bajo múltiples instancias) | Alta si se agrega una segunda instancia sin diseño previo | Redis Pub/Sub como backplane de difusión entre instancias desde el día 1, no como optimización posterior. Ver [ADR-002](adr/ADR-002-postgres-fuente-de-verdad-y-redis-como-soporte.md) |
| R-03 | Pérdida de eventos durante una desconexión breve del cliente (túnel WS caído unos segundos) | Medio (el usuario ve estado desactualizado) | Alta (redes móviles, wifi inestable) | Snapshot completo al reconectar en vez de intentar reproducir el stream exacto de eventos perdidos. Ver [ADR-008](adr/ADR-008-snapshot-mas-delta-para-reconexion.md) |
| R-04 | Redis Pub/Sub no persiste mensajes: si un suscriptor no está conectado en el instante del publish, lo pierde | Bajo si se combina con R-03 | Alta (es el comportamiento normal de Pub/Sub) | Aceptado deliberadamente: Pub/Sub es solo difusión en tiempo real, no el log de verdad. El log de verdad es Postgres. Ver [ADR-009](adr/ADR-009-redis-pubsub-vs-streams-para-fanout.md) |
| R-05 | Construir infraestructura de streaming de video propia consume el tiempo del proyecto sin aportar al objetivo técnico central | Alto para el cronograma del portfolio | Alta si no se acota expresamente | Fuera de alcance del MVP: integración simple de una URL externa. Ver [ADR-005](adr/ADR-005-transmision-en-vivo-fuera-de-alcance-del-mvp.md) |
| R-06 | Un cliente malicioso manipula el monto o el estado de una oferta desde el frontend | Alto (fraude directo) | Media | Toda regla de negocio se valida exclusivamente en el servidor (RNF-11); el cliente nunca es fuente de verdad |
| R-07 | Shill bidding: el propio rematador (o un cómplice) oferta para inflar el precio de su propio lote | Alto para la confianza en la plataforma | Media | Fuera de alcance de detección automática en el MVP; se deja como riesgo de negocio documentado y como ítem de roadmap (sistema anti-fraude). El registro inmutable de ofertas (RF-25) es la base necesaria para poder auditarlo después |
| R-08 | Fuga o exposición del JWT si se pasa como query param de la URL del WebSocket (queda logueado en proxies/logs de acceso) | Medio-alto (secuestro de sesión) | Media si no se diseña con cuidado | Autenticación en el primer mensaje del WS o vía subprotocolo, evitando tokens largos en la URL. Ver [ADR-006](adr/ADR-006-autenticacion-jwt-en-http-y-websocket.md) |
| R-09 | Ataques de spam de ofertas (bombardeo de mensajes WS) degradan la experiencia de todos los conectados a un remate | Medio | Media | Rate limiting por usuario/conexión en Redis (RNF-13) |
| R-10 | Ambigüedad de zona horaria en la fecha programada de un remate (rematador y comprador en distinto huso horario) | Bajo pero genera confusión de usuario | Media | Toda fecha se almacena en UTC y se resuelve a hora local en el cliente; no se resuelve en el backend |
| R-11 | Testing de lógica concurrente (condiciones de carrera) es intrínsecamente difícil de automatizar de forma determinística | Medio (riesgo de regresión no detectada) | Alta si no se invierte tiempo específico en esto | Tests de integración dedicados que disparan ofertas concurrentes reales contra Postgres, no solo tests unitarios de la función aislada |
| R-12 | Microservicios prematuros agregan complejidad operativa (deploy, tracing distribuido, consistencia entre servicios) sin necesidad real a esta escala | Medio para mantenibilidad y para el cronograma | Alta si no se decide expresamente lo contrario | Monolito modular con límites de módulo claros desde el diseño. Ver [ADR-001](adr/ADR-001-modular-monolito-vs-microservicios.md) |
| R-13 | Caída de una instancia backend durante un remate `LIVE` deja el estado del lote solo en memoria de esa instancia | Alto si el estado no está en Postgres | Baja-media | Todo estado de negocio (lote abierto, oferta vigente) vive en Postgres, nunca únicamente en memoria de proceso; una instancia nueva puede tomar cualquier remate reconstruyendo su estado desde ahí |
