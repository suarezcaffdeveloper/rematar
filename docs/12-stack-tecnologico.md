# 12 — Justificación del Stack Tecnológico

| Tecnología | Rol en el sistema | Por qué esta | Alternativas consideradas y por qué no |
|---|---|---|---|
| **Python + FastAPI** | Framework de backend | Soporte async nativo de primera clase (crítico para bidding/WebSockets concurrentes), tipado con Pydantic, generación automática de documentación OpenAPI, ecosistema maduro | Django: excelente para CRUD tradicional pero su ORM y ciclo de request síncrono por defecto pelean contra el caso de uso central (tiempo real concurrente); Node/NestJS sería válido técnicamente pero el objetivo del portfolio es demostrar dominio de Python en un contexto async real, no evitarlo |
| **SQLAlchemy** | ORM / capa de acceso a datos | Control fino sobre transacciones y locking explícito (`SELECT FOR UPDATE`), necesario para [ADR-004](adr/ADR-004-concurrencia-en-determinacion-de-ganador.md); soporte async maduro | Un ORM más "mágico" (ej. Tortoise) esconde justamente el control transaccional que este proyecto necesita mostrar |
| **Alembic** | Migraciones de esquema | Estándar de facto junto a SQLAlchemy, migraciones versionadas y reversibles | Editar el esquema a mano viola RNF-18 directamente |
| **PostgreSQL** | Base de datos relacional, fuente de verdad | Transacciones ACID reales y locking a nivel de fila, imprescindible para resolver condiciones de carrera en ofertas de forma correcta (no aproximada) | MongoDB u otra NoSQL: sin transacciones multi-fila tan maduras ni el mismo nivel de garantías para el caso crítico de negocio (determinar un ganador sin ambigüedad) |
| **Redis** | Pub/Sub para fan-out en tiempo real, cache de lectura, rate limiting, presencia | Es la pieza estándar de la industria para exactamente este problema (backplane de tiempo real entre instancias), con latencia sub-milisegundo | Usar solo Postgres `LISTEN/NOTIFY`: funciona a baja escala pero no está pensado para el volumen de fan-out ni para rate limiting eficiente; Kafka: correcto para event streaming pesado, pero es sobre-ingeniería operativa para el volumen y el objetivo de este proyecto |
| **WebSockets (nativos de FastAPI/Starlette)** | Canal de tiempo real bidireccional | Control total del protocolo de mensajes, sin una librería que abstraiga rooms/reconexión y oculte el "cómo" — justamente lo que este proyecto quiere demostrar que se sabe resolver | Socket.IO: da reconexión automática y salas gratis, pero es una dependencia pesada en frontend y reduce el valor demostrativo de diseñar el protocolo propio (ver [ADR-003](adr/ADR-003-websockets-nativos-vs-socketio.md)) |
| **JWT** | Autenticación stateless | Escala horizontalmente sin estado de sesión compartido entre instancias, coherente con RNF-05 | Sesiones server-side con store compartido (ej. Redis-backed sessions): viable, pero agrega una dependencia de lectura en el path de cada request autenticado que JWT evita |
| **Pydantic** | Validación y serialización | Integrado nativamente a FastAPI, tipado estricto en los bordes del sistema (RNF-11: nunca confiar en el cliente) | — |
| **React + Vite** | Frontend | Vite da un ciclo de desarrollo rápido; React tiene el ecosistema más maduro para manejar estado de UI reactivo ante eventos entrantes por WebSocket | Next.js: aporta SSR que este proyecto no necesita (la app es mayormente interactiva post-login, no orientada a SEO) |
| **Docker + Docker Compose** | Entorno reproducible | Levanta backend + Postgres + Redis + frontend con un solo comando (RNF-19), igual en cualquier máquina | — |

Nota: esta tabla se actualiza si el roadmap ([13-mvp-y-roadmap.md](13-mvp-y-roadmap.md)) incorpora
tecnología nueva (ej. Kubernetes, un message broker más pesado, un motor de búsqueda). Hasta
entonces, este es el stack completo — no se agrega nada "por las dudas".
